# Scale verification: 480x480 / 480x720 / 720x480

This directory exists because of one specific request: verify the design
against a minimum image size of 480x480 (square) and 480x720 (portrait) /
720x480 (landscape), and fix whatever real errors that turns up. It found
two.

## Bugs found and fixed

1. **`MAX_W`/`MAX_H` in `rtl/barrel_pkg.sv` were 512.** 720 (needed for
   the portrait/landscape long edge) exceeds that -- the design's frame
   buffer and coordinate width (`COORD_W`) were architecturally too small
   for the requested sizes. This would have silently produced wrong
   addresses for any dimension over 512. Fixed by raising both to 720,
   with `ADDR_W`/`COORD_W` (computed from them) following automatically.
   This is a real, shipped RTL fix -- not specific to this test directory
   -- see `rtl/barrel_pkg.sv`.

2. **A test-harness bug in this directory's own bounded-capture
   generator** (`gen_bounded_test.py`), not the RTL: the first version
   used `fork ... join_any` between the input-streaming task (fast,
   completes in full regardless of the output side) and the bounded
   output-capture task (deliberately stops early). `join_any` returned as
   soon as the FAST task finished, long before the bounded capture had
   gathered its target pixel count -- so most of the "captured" buffer
   was actually its zero-initialized default, compared against real
   golden data, producing a spurious near-total mismatch (253677/255000
   channels wrong) that had nothing to do with the RTL. Fixed by running
   the input stream detached (`fork ... join_none`) and awaiting the
   bounded capture directly.

## Why two kinds of test here

Measured wall-clock throughput on this simulator (Icarus 12.0, this
project's usual toolchain) at three points in the design:

| path | measured throughput | time for one 480x480 frame | time for one 480x720 frame |
|---|---|---|---|
| bilinear + MODEL_RADIAL | ~5,620 px/s | ~41s | ~61s |
| bicubic (any model -- paced, not full-throughput) | ~345 px/s | ~11 min | ~17 min |
| MODEL_FISHEYE/PANORAMIC/PERSPECTIVE (per-pixel divide "slow path") | ~161 px/s | ~24 min | ~36 min |

Bilinear+radial frames are fast enough to run to genuine 100% completion
within a normal simulation session. Bicubic and the three per-pixel-
divide models are not -- a single frame can take tens of minutes, which
this project's automated tooling cannot practically wait for on every
run. Rather than silently shrinking the image size for those cases (which
would defeat the point of this exercise), each of those tests configures
the DUT for the TRUE requested size and lets it stream a real, large
prefix of output (tens of thousands of pixels, spanning the *entire*
x-coordinate range from row 0 onward, plus dozens of full rows) before
checking bit-exactness -- catching the same class of addressing/width bug
a full run would, without requiring full completion.

## Files

- `tb_scale_barrel_square.sv` / `_portrait.sv` / `_landscape.sv`,
  `tb_scale_pincushion_square.sv` / `_portrait.sv` / `_landscape.sv` --
  full end-to-end pipeline (AXI-Stream in, frame buffer, AXI-Lite config,
  AXI-Stream out), streamed and captured to **100% completion**, at the
  true requested size, bilinear interpolation, MODEL_RADIAL (barrel and
  pincushion). Generated by `gen_scale_test.py`.
- `tb_bounded_bicubic_radial.sv`, `tb_bounded_fisheye.sv`,
  `tb_bounded_panoramic.sv`, `tb_bounded_perspective.sv` -- same full
  pipeline, true requested size, but capture stops after a bounded pixel
  count rather than requiring the whole frame. Generated by
  `gen_bounded_test.py`.
- `run_scale_verify.sh` -- builds and runs all ten (or a `fast`/`bounded`
  subset -- see the script's own usage comment). **Budget ~25 minutes**
  for the full set.

Additionally, `tb_verilog/tb_smoke.sv` and `ip/coord_gen/tb_coord_gen.sv`
both got a new section directly exercising `coord_gen.sv` at the exact
boundary coordinates these frame sizes need (x,y up to 479/719) for all
four implemented models (radial, fisheye, panoramic, perspective) --
fast (no streaming needed), and the most direct test of the `COORD_W`/
address-width concern specifically. Both pass in full (38/38 and 39/39
points respectively).
